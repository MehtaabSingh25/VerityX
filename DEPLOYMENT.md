# VerityX deployment: Vercel + Render

This deployment layout runs the Next.js frontend on Vercel and the FastAPI API, Celery worker, and transactional outbox dispatcher in one Render Docker web service. PostgreSQL and Redis-compatible Key Value are managed Render services. The API service uses a persistent disk for uploaded evidence and the Hugging Face model cache.

## Important constraints

- Deploy one Render API instance only with this local-disk layout. API, worker, and dispatcher intentionally run in the same container so they share `/var/data/media`. Do not scale this service horizontally. A multi-instance deployment requires shared object storage (S3-compatible) and corresponding application storage changes.
- Smaug is CPU-heavy and adds substantial image/model memory use. The Render plan must have enough RAM and disk for the model, Python dependencies, and media. Start with a paid plan and monitor memory; free instances are not a reliable target for this workload.
- Vercel serverless request bodies are size-limited. The patch sends evidence uploads directly from the browser to Render when `NEXT_PUBLIC_VERITYX_API_URL` is configured. All other API calls continue through the Vercel same-origin proxy. Configure the exact Vercel origin in Render `CORS_ALLOWED_ORIGINS`.
- AI detection is probabilistic and must not be represented as proof.

## 1. Deploy the backend on Render

1. Push this repository to GitHub.
2. In Render, create a Blueprint from the repository and select `render.yaml`.
3. Review the PostgreSQL, Key Value, and web-service plans/region. The sample uses Singapore; change region if needed so services are colocated.
4. Set `CORS_ALLOWED_ORIGINS` on `verityx-api` to the exact Vercel origin, e.g. `https://your-project.vercel.app` (comma-separate preview/custom origins only if required).
5. Set `SERPAPI_API_KEY` if Google Lens search is enabled. Leave blank to use the existing fallback provider.
6. Confirm Render has provisioned the persistent disk at `/var/data/media`.
7. After deploy, verify `https://<render-service>.onrender.com/health` returns `healthy`. The health check requires both PostgreSQL and Redis.

Render supplies `DATABASE_URL`; the backend normalizes `postgres://` and `postgresql://` to the psycopg 3 SQLAlchemy driver. The `API_KEY` is generated by Render and is not exposed to the browser. Database migrations run automatically at container startup before the API, worker, and dispatcher are launched.

## 2. Deploy the frontend on Vercel

1. Import the same GitHub repository into Vercel.
2. Set **Root Directory** to `frontend`. Framework preset should be Next.js; install/build defaults are `npm install` and `npm run build`.
3. Add these Environment Variables for Production (and Preview if desired):
   - `VERITYX_BACKEND_URL` = `https://<render-service>.onrender.com`
   - `VERITYX_API_KEY` = the generated Render `API_KEY` value
   - `NEXT_PUBLIC_VERITYX_API_URL` = `https://<render-service>.onrender.com`
4. Redeploy after adding variables.
5. Ensure Render `CORS_ALLOWED_ORIGINS` includes the exact deployed Vercel origin.

The service key is server-side only. Never prefix it with `NEXT_PUBLIC_`. The public API URL contains no secret; it is used only for direct media upload.

## 3. Verify production

- Open the Vercel URL and confirm the application loads.
- Confirm the backend health indicator succeeds.
- Create an investigation, upload a small image, and confirm it appears in the evidence inventory.
- Submit integrity, metadata, similarity, and AI-detection jobs and confirm worker results/events.
- Restart the Render service and confirm uploaded evidence remains available (persistent disk).
- Check Render logs for API, Celery, and outbox process failures.

## Operational notes

The API, Celery worker, and outbox dispatcher are supervised by `backend/run_render.py` in a single Render service. This is a pragmatic single-instance deployment for the current filesystem-based architecture, not a horizontally scalable topology. The worker runs with concurrency 1 to limit memory pressure from Smaug.
